## Official source review and limits

and its 36 links on 2026-10-06, including current names/new expressive entries.

dialogs, progress indicators and cards. Other catalog destinations were indexed,
not individually read end-to-end. App-bar indexed official content was reviewed.

inspection. Direct text fetch of Material pages returned JavaScript-only content;
the browser provided the relevant catalog/overview content instead.

Provider evidence reviewed: Material Web official README/roadmap/support, Angular
Components official repository/support statement, Material UI overview/component/
platform/theme/RTL documentation and repository. Bundle guidance was consulted
as documentation, not measured product performance. Some initially attempted
provider URLs returned unavailable/not-found; canonical links were resolved from
official pages where needed. No community comment was treated as provider policy.

[Material Web roadmap](https://github.com/material-components/material-web/blob/main/docs/roadmap.md)
reports maintenance and unavailable components; historical card preview is not
stable API proof. [Material UI overview](https://mui.com/material-ui/getting-started/)
identifies M2 support, not automatic M3/Expressive conformance.
[Angular Components](https://github.com/angular/components) identifies its
framework-bound maintained packages and support policy; exact current Expressive
coverage/runtime theme APIs remain an adoption-time check, not established here.

## Authored worked fit decisions — not forward-agent results

For raw **Work Visits**: recommend extending native controls/CSS-variable primitives
for the requested note/save/retry/dialog workflow. Reuse approved Inter/navy and
actual English LTR. Keep labeled save, recoverable input and real confirmation
semantics; no new admin. Nearest alternative is Material Web baseline primitives:
available relevant components do not justify a new provider absent a demonstrated
gap, and incomplete navigation/content coverage plus maintenance increases exit
cost. Required browser, keyboard/touch, shadow/form/SSR and bundle evidence is
still unmeasured; this is a plan, not an adoption/runtime pass.

For raw **Learn Together**: retain existing React/Material UI and approved token
resolver if its installed primitives meet text-field/dialog requirements. Keep
Vazirmatn/Persian RTL/spacious plum baseline. A personalized presentation can reuse
it while disclosing M2-to-requested-Material differences; do not assert newer
Expressive APIs. Nearest alternative is a second web-component provider, which
would add integration/duplicate theming work without an evidenced need. Verify
installed revisions, portal direction, actual fonts/weights and theme/state
consumption before implementation; no new picker/sheet admin choice is claimed.
Missing data blocks a final dependency decision, not the local instruction work.

For raw **Records View**: retain host-native table/chart behavior and existing
theme adapter. Label these custom/provider patterns; do not claim catalog support
or install Material Web as a complete replacement. For unknown-stack prospective
work, leave library undecided and ask only decision-critical context gaps.

Actual repository decision: this Skill is an instruction/resource package, not
a product runtime. No React/Angular/Material Web dependency is selected or needed
for R9.3. The guides offer a bounded, evidence-driven adoption procedure; hypothetical
product choices do not approve a stack for an unspecified real customer.

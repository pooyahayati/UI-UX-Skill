Use Aria Icons as an optional development-time discovery and comparison catalog. Keep the approved React/shadcn dashboard, coherent icon family, semantic assignments, and owner configuration as the baseline. A static icon remains a valid outcome; no package or asset needs selecting yet.

1. **Shortlist only where there is a concrete gap.** Compare alternatives for an unclear semantic use, missing state, or insufficient family coverage. Prefer assets from the existing family and compare actual size, stroke/fill, optical weight, and legibility in the affected control. Retain the current assignment when an alternative offers no demonstrated benefit. Do not import the catalog, enable its MCP/CLI, fetch icons remotely at runtime, or adopt a new visual style from its examples.

2. **Admit individual assets through the existing boundary.** Before adoption, inspect each selected asset's upstream family/name, revision, actual SVG, license, and attribution requirements. The catalog's code license does not establish every collection's asset terms. Only validated, prepared assets enter the allowlist; unknown terms and arbitrary SVG/code/URL uploads stay outside it. Record the proposed delta in the existing design decision record when implementation is authorized.

3. **Preserve configurable meaning.** Resolve approved assets through the existing semantic icon adapter, including independent consumers. An owner changing a picture must not change the operation, accessible name, or business state. Reuse the current gallery and draft/preview/validation/publication/history/rollback lifecycle. Preserve saved assignments and historical snapshots; missing coverage needs a meaningful known fallback with its identity visible to the owner. Do not add a competing settings panel or runtime library selector.

4. **Treat morph examples as candidates for a useful state transition.** A menu/close pair could clarify an existing disclosure, if that interaction exists. Start with current static/CSS behavior; consider morphicons only if it solves a demonstrated gap. Avoid routine motion across dense or frequently repeated dashboard actions.

   The supplied Skill's November 2 source notes describe an Aria exporter using morphicons `^1.7.0` that rejects filled/unsupported inputs, while engine `2.0.2` adds filled-shape support separately. That does not make the older exporter compatible. Recheck and pin the chosen exporter and engine independently; do not assume every catalog icon can morph.

5. **Propose a bounded trial before rollout.** Exercise the actual accepted pair and a rejected input, static/provider-failure fallback, rapid interruption, keyboard/focus, accessible names and expanded/pressed state. Keep success tied to confirmed business results. Explicitly configure reduced motion: the documented engine default is `never`. Respect the existing owner/user/OS policy, support immediate off states, and settle an active animation when preferences change. Clean up drivers/listeners; application behavior must not depend on animation completion.

Proposed checks also include actual owner save/reopen/reset/rollback consumers, invalid IDs and load failure, supported themes and narrow/wide English layouts, added route payload, and observed mobile interaction against the baseline.

This recommendation uses the supplied dashboard, icon-adapter, runtime-governance, accessibility, and motion guidance. No secondary product route or broad dashboard mode redesign is needed. No product files changed or packages installed. The product, live catalog, current licenses/APIs, rendering, accessibility behavior, and performance were not inspected or tested; these remain adoption checks.

Use subtle layout motion to show where a task lands, with a non-drag path and clear text feedback available throughout. Treat this as a React web application that also runs in mobile browsers; a narrow viewport does not require a native-mobile design route.

For coordinated insertion and reordering, Motion for React is a reasonable provider candidate if the existing stack has no suitable animation capability. This is a concrete use for layout continuity. Reuse an existing compatible engine first, and keep simple focus or status styling in CSS. Before adopting a dependency, inspect the actual components, package manifest and lockfile, then verify official APIs, compatibility, maintenance, license, security implications and route payload. None of those adoption checks can be completed from this prompt.

Keep the behavior small and purposeful:

| Event | Proposed treatment | Information that remains without animation |
| --- | --- | --- |
| A task is created | Briefly reveal the new card and move only the affected visible neighbors into place. | The task title, destination column and position; distinguish pending creation from confirmed creation. |
| The user reorders or moves a task | Show the target insertion point during manipulation, then settle the task and affected neighbors into their new positions. Keep subsequent commands immediately available. | A result such as “Review brief moved to Doing, position 2 of 5.” Keep selection and focus attached to task identity. |
| A task changes remotely | Use a restrained one-time cue when it is visible and safe to update. Batch bursts into a concise update notice. | A textual change summary and a way to locate the changed task. No focus theft, unsolicited scrolling or continuous pulsing. |

For an offscreen or filtered-out destination, explain where the task went and provide a user-triggered “Show task” action. Do not silently clear filters or jump the viewport. A temporary highlight can supplement this information, but neither color nor animation should carry it alone.

Every task should have a visible, labeled “Move” action usable by touch, mouse and keyboard. Offer a destination column and position, or straightforward “Move up” and “Move down” controls where sufficient. Use native buttons and controls where possible. Give drag users cancellation and a clear drop target, while keeping ordinary page scrolling usable outside the drag handle. Keyboard users must be able to complete the same move without a precision gesture. If a move picker opens, manage its initial focus, dismissal and focus return; announce the resulting task location through a restrained status region.

Use stable task IDs as React keys. Update logical order independently of animation, and keep DOM reading order consistent with the committed order. Animation completion must never trigger the mutation, validation, cleanup or focus restoration. Rapid moves, cancellation, unmounting or a disabled animation must leave a usable board without duplicate actions. If moving between columns remounts the focused control, restore focus meaningfully to that task after the user-initiated move.

Remote changes need an explicit concurrency policy. If another update affects the task being edited or moved, preserve the local work and expose the conflict using the backend's actual versioning and reconciliation capabilities. Avoid moving a target out from under an active gesture. Pending local moves, server confirmation, failure and uncertain/disconnected state must remain distinguishable. On failure, reconcile to authoritative state with persistent recovery feedback; a rollback must not erase a newer remote change. Do not promise locking, merging, Undo or safe retries unless the system supports them.

Resolve motion consistently across the board, CSS and any provider-controlled components. Respect the operating system's reduced-motion preference on initial load and when it changes. Reduced motion should replace spatial movement with an immediate layout update and clear static location/status feedback; a brief non-spatial effect is optional. If the product already supports an off setting, it must also disable fades. Motion's reduced-motion configuration alone is not a complete off policy. A product default must never override a request for less motion. Reuse established duration/easing tokens, and start with a static usable state while preferences are unknown. This scoped recommendation does not require a new settings panel.

On mobile, verify these interactions on representative real devices and supported browsers, alongside responsive browser checks:

1. Create and reorder at the top, middle and bottom of a populated board, including moves between columns and destinations outside the viewport. Confirm that users can identify the task's final location in normal, reduced and off modes.
2. Complete the same workflow with visible move controls, an external keyboard and mobile screen readers. Check accessible names, useful position announcements, focus continuity and freedom from repeated announcement noise. Test practical touch targets and drag cancellation without breaking vertical scrolling or pinch zoom.
3. Interrupt a transition with another move, a preference change, rotation, navigation or a remote update. Verify correct order, preserved selection and drafts, immediate responsiveness and no hidden input-blocking elements. 4. Simulate slow confirmation, rejection, disconnection, reconnection and concurrent changes to the same task. Check truthful pending/error states, preserved work, conflict recovery and safe retry behavior. Confirm that passive updates preserve focus and reading position.
5. Profile a realistically long board and bursts of remote updates on a representative lower-powered phone. Compare before/after interaction latency, dropped frames or long tasks, rendering work, memory and route JavaScript payload against the project's baseline. Avoid per-frame full-app React state updates and animation of every offscreen card. Preserve existing virtualization if present; add it only when measurements justify it.

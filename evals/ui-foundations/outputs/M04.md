Use the most restrictive effective motion policy. The owner's setting is the product ceiling; a personal preference can lower it, and operating-system reduced motion is an accessibility constraint that the owner cannot override.

| Published owner setting | Personal setting | OS preference | Effective behavior |
| --- | --- | --- | --- |
| Standard | Standard or inherit | Reduced motion | Reduced-motion treatment; no large movement, parallax, or looping effects. Immediate changes or a brief non-spatial alternative may communicate state. |
| Off | Standard | Either | Off, including fades. A personal setting cannot exceed the product ceiling. |
| Any | Off | Either | Off, including fades. Neither owner standard nor an OS change can re-enable animation. |

Keep the established `off`, `subtle`, and `standard` presets, or their accepted equivalents. Subtle is a product preset, not proof that reduced-motion requirements are satisfied. Resolve validated settings conceptually as follows:

```text
configured level = lower of owner ceiling and personal level
                   (inherit uses the owner level)
if configured level is off: effective policy = off
else if OS requests reduction: effective policy = reduced treatment
                              bounded by the configured level
else: effective policy = configured level
```

Off means immediate visual state changes with no animated transitions, fades, spinning, pulsing, shimmer, or decorative loops. It does not remove feedback, delay focus, disable actions, or stop the underlying operation. Standard still permits only purposeful, bounded motion.

Resolve this once through the existing settings/token boundary and expose the same effective policy to every motion consumer. Keep the saved personal choice separate from its effective result, while validating it against the current schema. Show concise explanations such as “Reduced by your device setting” or “Motion is off for this product.” Reset re-resolves against current settings; it never bypasses the OS preference. An actually removed or invalid option follows an explicit migration or safe fallback.

The implementation contract must cover these consumers:

| Consumer | Required behavior |
| --- | --- |
| CSS transitions, keyframes, pseudo-elements, and loaders | Consume the resolved policy through scoped attributes/tokens and appropriate CSS rules. Reduced mode removes spatial and looping effects; off removes all animated transitions, including opacity. Replace a spinner or shimmer with a stable loading indicator and text. Keep busy/status semantics; show measured progress only when real progress exists. |
| Animated icons | Stop spins, pulses, and morphs as required. Render the correct static pending, success, error, expanded, or collapsed symbol. Preserve accessible labels and semantic state; do not freeze an arbitrary in-between frame or turn a loading icon into an apparent success state. |
| Sheets, dialogs, tooltips, and other overlays | Supply the current policy to their actual render roots and animation adapters, including portal containers or independent mounts outside the main tree. Verify provider/context and CSS reach instead of assuming a main-wrapper setting covers them. Preserve keyboard behavior, dismissal, focus, and background interaction rules. |
| Imperative and third-party animation consumers | Pass or subscribe to the same policy and explicitly cancel or settle active effects. A provider does not automatically govern CSS, independent animation calls, or every copied component. Use a supported static alternative if a consumer cannot honor the policy. |

Reuse the current stack; this specification does not select or require an animation dependency. If Motion is already used, its reduced-motion provider support alone is insufficient for owner-selected off: the candidate guidance notes that opacity can remain animated. Explicit off behavior is still required across all claimed consumers. Avoid a blanket tiny-duration workaround that relies on completion events or leaves components in intermediate states.

Read the OS preference before starting motion and subscribe to changes, for example through the browser's `prefers-reduced-motion` media query. Re-resolve on OS, published owner, or personal preference changes. Start with a static, usable state while preferences are unknown, avoiding an initial animation burst. Configuration-load failures must retain a safe last-valid/default policy and cannot override a known request for less motion. Remove subscriptions and active animation work when their scope ends.

If the OS preference changes while a sheet is closing, the requested closed state remains authoritative. When reduction becomes enabled, cancel the spatial exit and settle directly to closed; do not restart the transition as another animation. This immediate completion is a valid reduced-motion treatment. The same path applies when owner or user settings switch to off. If the OS changes back to no preference during closing, finish the current safe close without replaying or upgrading it; subsequent interactions may use the newly resolved policy.

Closing must have an explicit, idempotent finalization path independent of `animationend`, transition duration, or an exit callback. It must remove the exiting sheet and backdrop, release that overlay's focus trap and background/scroll locks, and restore focus to its trigger or an appropriate available destination. Respect any other open modal's locks. No invisible overlay may intercept input, and leaving content must not remain keyboard reachable. A transition identifier or equivalent state guard must prevent a stale close callback from removing a newly reopened sheet. Mutations, navigation, validation, and preservation of drafts remain independent of animation completion; cancelling motion must not repeat the underlying action.

Use the already authorized appearance panel's existing permissions and lifecycle: private draft and preview, validation, publication, reopen, reset, history, and rollback. A preview must not change other users' effective settings. Accept only approved motion presets; no arbitrary animation code, timings, or runtime library selector is needed. Published settings and personal preferences retain their existing scopes.

Before accepting an implementation, verify the three cases in the table through the real panel and inspect a CSS loader, an animated icon, and an overlay outside the main tree. Also exercise OS changes in both directions during closing, rapid close/reopen, absent completion callbacks, initial configuration loading, invalid/failed configuration, persistence after refresh, and reset/rollback. Confirm that off produces no remaining animation, static loading/status stays truthful, focus returns correctly, drafts survive, and no backdrop or scroll lock remains. Check keyboard and screen-reader behavior separately from visual inspection; a screenshot alone cannot establish the interruption behavior.

This is a proposed behavior contract, not an implemented or tested product change. With the host/product type unspecified, I used the `generic-product-ui` fallback with no secondary route or Product Pack. The relevant shared rules were motion, accessibility interaction, state/recovery, and feedback/status; design-system guidance covered tokens, component states, and runtime governance. Other Product Packs and unrelated visual modules were not loaded. No product-language specialist was required by this English specification. Only the supplied candidate guidance was inspected: no product code, rendered interaction, automated test, accessibility conformance, provider compatibility, or runtime setting persistence was verified. Implementation and those checks remain the next engineering step; the panel's existing authorization is accepted.

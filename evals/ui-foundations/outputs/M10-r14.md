Use one resolved motion policy for this React web application, with a static, usable server-rendered baseline. Motion must never determine whether an action, navigation, or state change succeeds.

1. **First render:** Treat the unknown client preference as a reason to defer animation. Render meaningful final visual states: visible content, truthful expanded/selected/busy states, working controls, and visible focus. Do not render essential content at opacity zero awaiting an entrance effect. Ship the initial motion gate in the server HTML/CSS so transitions and copied controls cannot start before hydration. An OS reduced-motion media query should also protect CSS consumers before JavaScript runs.

2. **Hydration:** The first client render must match the server’s markup and initial policy. Do not branch that render on browser-only preference APIs or suppress hydration warnings as a fix. After hydration, read and subscribe to the OS preference, validate available configuration, then resolve the effective policy. The owner setting is a ceiling; personal preferences can lower it, and OS reduction remains authoritative. Keep the static fallback while necessary inputs are unknown. Enabling permitted motion should affect subsequent interactions, without replaying entrance animations or flashing hidden content. Preference changes during animation must cancel or settle active motion immediately into the correct semantic state.

3. **Every consumer:** Apply the resolved policy through shared adapters to CSS transitions/keyframes, library components, copied animated controls, icons, imperative animations, and portals. A provider alone does not cover them all. Audit copied source for hard-coded durations, loops, entrance states, exit retention, and bypasses. Reduced motion replaces substantial movement, parallax, and loops with immediate changes or appropriate brief non-spatial feedback. **Off** disables all animated transitions, including fades, while preserving static progress/status and all actions. If Motion is already used, its documented `reducedMotion="user"` behavior is useful but does not implement full off mode because opacity animation can remain. Verify the installed API before implementing its adapter.

4. **Configuration failure:** Validate loaded values before resolution. Retain a compatible, correctly scoped last-valid configuration or safe defaults, reapplying current OS/user restrictions. If no safe policy is established, remain static. Missing, malformed, partial, or failed loads must not increase motion, leak a private preview, overwrite saved settings, or produce a false saved/published state. Keep the application usable and expose appropriate recovery without inventing a new settings panel.

5. **Route cleanup:** Unsubscribe route-owned listeners, cancel animation drivers, frames and timers, disconnect observers, and abort or ignore obsolete route requests. Make cleanup idempotent. Remove exiting overlays and release focus traps/scroll locks through the primitive’s supported lifecycle; no invisible layer or hidden focusable content may remain. Restore or move focus according to the destination. Never depend solely on `animationend`, transition duration, or exit callbacks for cleanup, validation, mutations, navigation, or focus. Preserve drafts and legitimate background work; do not duplicate actions.

Proposed checks: cold SSR with delayed/disabled JavaScript; hydration diagnostics; normal/reduced/off across CSS and copied controls; preference changes mid-transition; failed/invalid configuration; rapid navigation and repeated activation; keyboard, focus, and overlay cleanup.

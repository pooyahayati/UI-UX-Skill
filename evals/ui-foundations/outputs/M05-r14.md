The current “off” preset violates its contract. `MotionConfig reducedMotion="always"` is only one adapter: Motion’s reduction can retain opacity animation, and it does not govern CSS fades or skeleton shimmer. Treat motion as optional presentation over a complete interaction state machine.

Define these contracts in the existing design documentation, linking the actual preset/token source:

- **Standard/subtle:** approved, purposeful motion that never delays essential interaction.
- **Reduced:** remove large displacement, parallax and looping effects; use immediate changes or a brief non-spatial alternative where useful.
- **Off:** no animated transitions, including fades, shimmer or icon morphs. Preserve visible focus, static loading indicators, status text and every action. “Saving…” plus a static placeholder remains meaningful without shimmer.

Resolve one effective policy from owner, permitted user preference and operating-system reduction. Owner settings are a ceiling; personal or OS requests can reduce motion further. Apply it to CSS, Motion, copied components and imperative consumers. Resolve safely before animation starts, use a static usable initial state while preferences are unknown, and cancel/settle active animations when the policy changes. Reuse existing architecture and dependencies.

Implementation should separate semantic state from visual lifecycle:

1. Validation, mutations, navigation and pending/result state must run independently of `animationend` or exit callbacks. Set required focus after the relevant content is mounted and usable, using the component’s supported lifecycle. Focus errors or new steps when appropriate; ordinary save confirmation should announce status without stealing focus. Closing overlays must release blocking layers and restore focus even with animation disabled or interrupted.
2. Model save outcomes explicitly: editing, validating, pending, confirmed success, known failure and uncertain outcome. Show “Saved” only after authoritative confirmation. Preserve drafts on failure and uncertainty; a late response must not clear newer edits or overwrite a newer operation.
3. A request timeout means confirmation was not received, not that saving succeeded or definitely failed. Explain the uncertainty, preserve input and offer status reconciliation or a safe retry according to the existing API. Prevent duplicate writes through existing request identity/idempotency support; do not silently change API semantics.
4. Guard activation synchronously, before asynchronous work or a rerender, and expose an understandable busy state. Rapid clicks or Enter presses cannot create duplicate saves, skip validation or advance multiple steps. Use operation identities to reject obsolete callbacks; cancel obsolete presentation work, settle to the current state and clean up timers/listeners on unmount. Debouncing alone is insufficient.
5. Any visual fallback timeout may settle presentation only, through an idempotent cleanup path. It must never decide save success, perform a mutation or be the sole route to focus recovery.

Proposed acceptance checks: exercise normal/reduced/off across all consumers; switch preferences mid-animation; test keyboard focus, static status announcements, rapid repeated activation, interrupted/unmounted transitions, suppressed completion events, delayed success, failure, timeout and late responses. Verify drafts and newer edits survive, no duplicate operations occur, and existing preview/save/reopen/reset/rollback controls update actual consumers.

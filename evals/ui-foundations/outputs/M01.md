**Save feedback**

Use one inline status area beside the save action. Reserve enough layout space to avoid the button and surrounding controls jumping between states, while allowing messages to wrap. Reuse semantic text/icon colors and keep the wording available without relying on animation or color.

| Actual outcome | Feedback | Behavior |
| --- | --- | --- |
| Request in progress | “Saving…” | Guard duplicate submission immediately; preserve the draft and keep unrelated dashboard controls usable. Use indeterminate feedback only. |
| Authoritatively confirmed save | “Saved” | A brief acknowledgement may appear. Mark only the submitted revision as saved. |
| Confirmed rejection or failure | Specific error and correction, such as “Changes weren’t saved. Check the highlighted fields.” | Preserve valid values. Restore the supported correction or safe retry action. |
| Timeout with unknown commit outcome | “We couldn’t confirm whether your changes were saved.” | Keep this message visible, retain the draft, and enter an explicit unknown state. Do not report success, assert that nothing was saved, or automatically resubmit. |

For the unknown state, use an existing read-only status/reconciliation path if the product has one. Offer “Check save status” only when that action can actually check the submitted operation or revision. A stale read or an unchanged record is not, by itself, proof that the original write cannot still commit. A confirmed result can resolve the state; an inconclusive result stays unknown.

Retry is appropriate only when the existing contract establishes that it is safe—for example, a supported idempotent retry of the same operation, or authoritative confirmation that the write did not commit and cannot still complete. A disabled save action needs a visible explanation and a supported recovery path. If the current product has no way to reconcile or safely retry, retain the uncertainty and flag that contract gap rather than inventing a status endpoint or adding a backend change to this polish task.

Tie responses to the submitted operation and draft revision. A late confirmation must not overwrite newer edits or mark them saved. Keep network outcome and dirty-state transitions independent of presentation timers, animation callbacks, and component unmounting. A local timeout or cancelled animation does not establish server cancellation.

Announce meaningful status changes through the existing restrained live-status mechanism without moving focus. Keep actionable failure and unknown messages durable; a transient toast may supplement confirmed success but cannot carry the only recovery instruction.

If the product already has an off setting, it must also remove fades and animated loading indicators while preserving static “Saving…” text, focus, and actions. Reuse any existing owner/user policy, with the least-motion applicable constraint winning. This small change does not need a new appearance panel or preference schema.

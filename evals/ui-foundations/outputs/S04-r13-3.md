For the explicitly redesigned settings surface, stable public `@wordpress/components` controls are the required candidate convention, even for a small form. They supply interaction primitives, while the actual option semantics determine the control:

| Need | Selection and reason |
| --- | --- |
| Short text or technical value | `TextControl`, with a persistent label, relevant input type, help, associated errors, and appropriate text direction. Preserve the stored value and validation contract. |
| Boolean option | `ToggleControl` or `CheckboxControl`, according to the option’s meaning. Make explicit-save behavior clear; changing the control edits the draft when that is the existing contract. Retain disabled dependent values. |
| Small fixed choice set | `SelectControl` or `RadioControl`, chosen for whether seeing all alternatives aids the decision. Preserve option values and available choices. |
| Save action | `Button`, with the existing submission scope, busy/disabled behavior, and protection against duplicate submission. |
| Save result or validation summary | Durable local `Notice` plus field-level errors. An unresolved failure must remain discoverable rather than exist only in a toast. |
| Secondary settings | Ordinary sections first. If genuine disclosure is needed, verify an appropriate stable public control for the supported hosts; do not automatically use inspector-oriented `PanelBody`. A documented native composition is acceptable for a demonstrated component gap. |

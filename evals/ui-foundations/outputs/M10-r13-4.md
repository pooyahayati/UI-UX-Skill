Use one resolved motion policy for every consumer, and start with a static, usable interface until client preferences are known. Treat unknown preferences as unknown, never as permission for full motion.

1. **Server render and first paint.** Render content in its meaningful resting state: visible text, usable controls, truthful loading/status indicators and the correct open/closed state. Do not render essential content hidden pending an entrance animation. Emit the same conservative policy and markup for the server render and the client's first render. Include static defaults in the initial CSS so transitions cannot run before JavaScript hydrates; suppress copied controls' initial/automatic animations as well. Reading browser preferences during the initial render to produce different markup is not a hydration strategy.

2. **Hydration and preference resolution.** After hydration, read the OS preference, load/validate configuration and any supported personal preference, then resolve a single effective policy. Keep motion off while a required input remains unknown. Subscribe to OS preference changes and recompute when settings change. Enabling motion should affect subsequent meaningful interactions; it should not replay entrance animations or briefly animate already rendered content. Applying policy attributes/tokens must itself avoid triggering a transition burst.

   Owner settings are a ceiling, personal settings may reduce it further, and OS reduction is a protected constraint. Owner standard plus OS reduced gets reduced treatment; owner off plus user standard remains off; user off remains off. Reduced treatment removes large spatial movement, parallax and loops, with a brief non-spatial alternative only where useful. Off means no animated transitions, including fades, while preserving static progress, focus and all actions.

   Apply this policy through explicit adapters for CSS transitions/keyframes, animated controls, icons, portals and imperative animation calls. A library provider does not automatically cover them all. Review copied controls for hard-coded transitions, entrance/exit behavior and completion callbacks. If using Motion, its reduced-motion setting alone is not a complete off implementation; independent CSS and other consumers still need their own policy integration. No new animation library is required merely to establish this contract.

3. **Configuration-load failure.** Keep the application usable with a validated, correctly scoped last-known-good snapshot, or a conservative bundled fallback if none exists. Resolve that fallback through the same OS/user restrictions; failure must not promote unknown, reduced or off to stronger motion. Retain known restrictive choices. If preferences cannot be determined, remain static. Reject malformed settings rather than applying fragments, preserve stored configuration/history, and retry without replaying animations or resetting user work. Track fallback/error state separately from a successfully loaded or published configuration.

4. **Interruption, route change and unmount.** A move to reduced/off must stop incompatible animations already running and settle each control into the current semantic state. On route change/unmount, dispose of route-owned animation handles, timers, animation frames, observers and subscriptions; abort or ignore obsolete configuration results. Keep app-owned subscriptions at their actual owner lifetime, without adding duplicates per route. Cleanup should be idempotent under repeated mount/cleanup cycles.

   Navigation, validation, mutations, focus restoration and overlay removal must work without an animation-completion event. Closing or leaving a dialog must release its focus trap, backdrop, scroll lock and hidden interactive content through the primitive's supported lifecycle. Restore focus to a valid destination; route changes may require the new page's focus target instead of a trigger that no longer exists. Preserve drafts and prevent duplicated actions when an animation is interrupted. Keep business state independent of visual completion.

Verify with a slowed or delayed client startup, reduced motion already enabled before loading, normal/reduced/off settings, preference changes mid-transition, configuration rejection/timeout, and navigation during both entry and exit. Exercise at least one CSS transition and one copied animated control, including keyboard focus and overlays. Check for initial motion bursts, hydration warnings, invisible blockers, duplicated listeners and delayed callbacks affecting the next route.

This is a behavior contract based on the web-application motion, accessibility and runtime-governance guidance. No application source was supplied, and no runtime, rendered or accessibility checks were performed.

## Resolution, privacy, and reliability

Apply locked product/accessibility constraints first, then design-system defaults, current published owner configuration, and permitted personal preferences. Treat the owner level as a ceiling, with users and the operating system able to reduce it further:

| Owner | User | Operating system | Effective result |
| --- | --- | --- | --- |
| Standard | Inherit | Normal | Standard |
| Standard | Subtle | Normal | Subtle |
| Subtle | Standard or an invalid stronger stored value | Normal | No stronger than Subtle; reconcile the invalid preference |
| Standard | Inherit | Reduced | Approved reduced-motion treatment |
| Off | Standard | Either | Off |
| Standard | Off | Either | Off |

Use a static usable initial state when configuration or client preferences are unresolved. Do not show an initial burst of stronger motion. Changes during an active transition must settle coherently. Validation, navigation, mutations, focus restoration, and cleanup must work without an animation-completion callback. Essential content and progress/status meaning remain visible when movement is removed.

Continue the existing lifecycle: **Edit private draft → Preview → Validate → Publish → Active revision**. Saving a draft is not publishing. Bind it to the actor, authorized scope, schema version, and base published revision. A second administrator may edit their own draft but must not read the owner's private draft merely because they share publication privileges. Enforce this on reads, writes, previews, and revision endpoints at the trusted boundary; keep private draft content out of public/shared caches and ordinary configuration responses. Cancel/discard leaves published state unchanged.

Publish one complete validated snapshot atomically. If administrators A and B start from the same revision and A publishes first, B's stale publication must return a conflict, preserve B's work, and show the current published changes for explicit reconciliation. Do not use last-write-wins for shared appearance governance. A rollback or reset publication participates in the same revision check. If a response is lost, show an uncertain outcome and reconcile the active revision/request before retrying; neither a success animation nor a timeout proves publication success or failure.

Version persisted presets and their migrations. Preserve valid existing values and intent; map renamed equivalents only through explicit, versioned migrations. Do not silently rename/reset old selections or reinterpret a removed preset as a different behavior. Unknown, corrupt, removed, or no-longer-permitted values resolve to a current allowed default after validation. Retain historical raw values only where necessary for audit/migration, never as active executable configuration. Reconcile stored user preferences after owner/schema changes and after rollback. Notify users when reconciliation materially changes their experience; do not announce harmless internal migrations.

For missing, partially invalid, incompatible, or failed configuration loads, preserve a compatible last-valid published snapshot for the same scope, or use known safe design-system defaults. Reapply the user's and operating system's lower-motion constraints. Never fall back to a private draft, combine incompatible snapshot fragments, or replace persisted configuration/history with the fallback. Clearly distinguish current published state, a private preview, and fallback/stale state in the control center. Preserve unsaved work and provide an actionable retry. If the base revision cannot be established, prevent publication until it can be reconciled.

Keep published versions reconstructable. Record actor, time, scope, schema/revision, changed fields, validation result, and relevant draft/publish/reset/rollback events without exposing private content unnecessarily. A rollback revalidates/migrates the historical snapshot under the current schema, presents its diff, and creates a new revision; unsafe or unmigratable history is not published. Scope and confirmation for broad resets must be clear, with cancellation leaving both active configuration and history intact.

Lose the response after commit: reconcile the actual revision before retrying, without duplicate publication/history or false success/failure feedback.

Before replacing anything, complete these checks:

1. **Review the exact source and integration diff.** Inspect the existing sheet, affected icon consumers and owner mapping, shadcn configuration, aliases, styling setup, package manifest and lockfile. Compare the chosen Animate UI component's actual primitive family and supported APIs with your current contracts, including any composition or mount-control props you use. Check the selected revision's official API documentation, framework and Motion compatibility, license, maintenance, and dependency/security implications at adoption time. Review generated files and dependency changes before accepting them. Do not regenerate or overwrite customized components, copy the whole registry, or install unrelated tooling. Record upstream source/revision and local deviations so future updates can be diffed.

2. **Keep motion policy effective across all consumers.** Resolve the existing product setting, any personal preference and OS reduced-motion request before animation runs; a request for less motion must remain effective. Apply that policy to CSS transitions, Motion components, copied Animate UI code, animated icons and independent consumers. Verify the installed version's behavior: the supplied guidance describes `MotionConfig reducedMotion="user"` as reducing transform/layout animation while still allowing values such as opacity. It therefore does not implement a complete off mode. Reduced mode needs a usable lower-motion alternative; off mode must also eliminate fades and icon loops while retaining static status and all actions. Handle preference changes during animation and avoid a first-render animation burst or hydration mismatch. Preserve existing settings; this change does not require a new appearance panel or runtime library selector.

3. **Exercise the sheet lifecycle and action semantics.** Test open, close, rapid reopen, interruption, route/unmount cleanup and close while a preference changes. Verify initial focus, modal focus containment where applicable, visible focus, keyboard access, Escape, explicit close/cancel, approved outside-click behavior, scroll locking and meaningful focus return. Exiting or hidden content must not remain focusable, and a closed sheet must not leave an invisible backdrop intercepting input. Preserve drafts and unsaved-change safeguards where present. Mutations, validation, navigation, cleanup and focus restoration must not depend solely on an animation-end callback. Repeated activation must not duplicate actions; success animation must follow a confirmed result, with pending, failure and uncertain outcomes still distinguishable.

4. **Verify owner icons through real consumers.** Exercise the existing mapping with representative owner selections, paired states and a missing/unsupported animated asset. The fallback must still communicate the same action. An individual page import must not bypass the shared adapter. Keep accessible button names and state exposure; decorative icon animation should not add duplicate screen-reader announcements. Preserve disabled behavior, focus rings and hit targets. Mirror only genuinely directional meanings, and check that RTL mirroring and animation transforms do not overwrite each other. No schema reset or replacement of saved owner assignments is justified by this integration.

5. **Compare rendered Persian RTL behavior with the approved baseline.** Check direction propagation into the actual primitive, portal and overlay, logical positioning, the approved sheet edge and its entrance/exit direction. Do not assume the root `dir` attribute resolves every overlay or blindly mirror all movement. Inspect real Persian labels, long text, mixed-script identifiers and adjacent punctuation at narrow, intermediate and wide widths, plus zoom. Preserve semantic reading and keyboard order, ordinary text reflow and reachable actions. Isolate technical LTR fragments without changing stored values; test editing/copying where those fields exist. Preserve Vazirmatn and its approved weights, line heights and spacing. Check font loading and actual rendered glyph/weight identity separately: a CSS family declaration alone is insufficient. Review the existing authorized themes; do not add a new locale or style variant for this task.

6. **Validate one representative integration before expansion.** Capture the existing sheet and icon states, then compare the adapted version in the same contexts. Exercise normal, reduced and off behavior through actual interaction, including keyboard, touch and available screen-reader checks. Run the project's relevant type, lint, build and interaction checks, plus an automated accessibility scan where available; keep manual findings separate from scan results. Measure the affected route's payload and representative mobile interaction cost against the baseline, checking duplicate Motion copies, unnecessary rerenders and competing animation control of the same property. Use the project's performance expectations rather than inventing a frame-rate claim. Keep the existing implementation recoverable until the selected replacement passes its scoped checks.

The replacement decision should be made from that source diff and rendered interaction evidence. If primitive compatibility or an accessibility contract fails, retain the existing sheet and adapt only the compatible motion treatment. Any broader foundation, primitive-family or dependency migration would be a separate decision.

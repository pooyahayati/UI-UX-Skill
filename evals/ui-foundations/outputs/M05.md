The current implementation does not satisfy an **off** preset. `MotionConfig reducedMotion="always"` requests reduced motion within its scope; it does not disable independent CSS animations, and reduced-motion behavior can retain opacity transitions. There is also a functional defect: focus and save confirmation must remain correct when an animation never starts, is interrupted, or never emits its completion event.

I would define the following contract for this targeted correction.

1. Make **off** an explicit, shared policy.

   Resolve the existing owner preset, any supported personal preference, and the operating-system preference once, then feed that result to all affected consumers. The owner preset is a ceiling; personal and operating-system accessibility preferences can reduce motion further. Owner off or personal off always resolves to off. Owner standard with OS reduced motion receives the reduced treatment. A configuration-load failure must not restore stronger motion than an already known preference permits.

   In off mode, render state changes immediately: no fades, transforms that animate, layout transitions, shimmer, pulsing loaders, animated icons, or smooth scrolling on the affected surface. Preserve necessary static positioning and transforms. Replace shimmer with a static placeholder and readable loading status; do not conceal ongoing work. Reduced motion can use an appropriate brief non-spatial alternative, but off cannot retain that fade.

   Adapt Motion components explicitly to their final semantic state, including opacity and exit behavior. Disable relevant CSS transitions and keyframes, including pseudo-elements, and cover portals, copied components and imperative animation consumers. A provider setting alone is insufficient. Switching to off during an animation must cancel it and settle at the latest intended state, with no invisible overlay or stranded intermediate opacity. Start with a usable static state while client preferences are unknown, and respond to preference changes at runtime.

2. Give interaction state ownership of behavior.

   Validation, navigation, saving, visibility, focus and resource cleanup must have lifecycle paths independent of `animationend`, `transitionend`, exit callbacks or elapsed animation duration. Animation observes the state change; it does not authorize or complete it.

   Move focus when the relevant semantic transition requires it and the destination has committed to the DOM. For example, after failed validation, focus the appropriate error summary or field; after opening a dialog, use its supported focus lifecycle; after closing it, restore focus meaningfully. Check that the request is still current and the target is mounted and usable. Never delay visible focus for a fade. A passive “Saved” message should normally be announced without moving focus.

   Derive visible, expanded, busy and disabled states from the same semantic model. Hidden or exiting content must not remain keyboard interactive, and an invisible overlay must not intercept input. Keep draft values and required validation intact during interruption and step changes.

3. Separate the save lifecycle from both animation and timeout.

   A useful state model is `idle -> validating -> pending -> confirmed | rejected | uncertain`. Invalid input returns to an editable error state without a mutation. A response that only accepts a background job remains pending until authoritative completion.

   | Event | Required result |
   | --- | --- |
   | Valid submission starts | Capture the submitted draft revision, acknowledge pending work, and start one operation. |
   | Authoritative save confirmation | Mark that submitted revision saved and present static, accessible confirmation immediately. |
   | Confirmed validation or save rejection | Preserve inputs, show the relevant error and explain recovery. |
   | Request times out or its response is lost | Show “Save status unknown” or equivalent; preserve the draft and reconcile the outcome. |
   | Animation finishes, is cancelled or times out | Settle visual housekeeping only; it cannot produce save success or failure. |

   Choose the request timeout from the existing service contract; it is unrelated to motion duration. A client timeout or abort does not prove that the server cancelled or rolled back a write. After an uncertain result, check the operation status or authoritative saved revision using the existing API. If reconciliation is unavailable, retain the uncertainty and explain the safe recovery limit instead of claiming failure or encouraging blind retry.

   Use the backend's existing idempotency and concurrency mechanism where supported. A retry of the same logical save should reuse its identity and payload; a changed draft is a new operation. For appearance publication, retain the base-revision check and atomic snapshot semantics. Do not claim duplicate-write protection from a frontend guard alone, or assume the backend supports these capabilities without inspecting it.

4. Define rapid-repeat and race behavior explicitly.

   Route pointer activation and keyboard form submission through one handler. Acquire a synchronous in-flight guard before asynchronous validation or saving; do not rely solely on a disabled button rendered on the next update, a debounce, or an animation finishing. Repeated activation of that operation is ignored or coalesced, with one coherent pending status. Preserve predictable focus and explain why another save is temporarily unavailable.

   Associate requests and transitions with operation IDs or generations. Each outcome is applied idempotently. Stale responses, timers and animation callbacks cannot clear a newer busy state, close a reopened panel, restore focus into an obsolete form, or overwrite newer feedback. A late result for the still-current uncertain save can resolve it after reconciliation. If editing remains available during saving, confirmation of the submitted snapshot must leave later edits dirty.

   For reversible presentation actions such as opening and closing a disclosure, settle to the latest valid intent. For form steps, repeated clicks must not bypass validation or skip steps. Clean up listeners, timers and animation handles on replacement or unmount without treating that cleanup as server cancellation.

5. Keep visual fallback bounded and harmless.

   If an existing component needs a watchdog for temporary visual remnants, use an idempotent finalizer that handles completion, cancellation, preference changes and a bounded fallback timeout. Off mode takes the immediate path. The fallback can release visual resources, but cannot invent a save outcome, trigger a mutation, or substitute for the semantic focus lifecycle. Avoid tiny fake durations intended to keep completion callbacks firing; remove the functional dependency instead.

   Use text and programmatic status for pending, confirmed, failed and uncertain outcomes. Keep actionable errors and uncertain-state recovery available. Deduplicate announcements and confirmations during repeated clicks; animation and color are supplementary feedback.

6. Accept the correction through behavior checks.

   Proposed checks are: all existing motion presets plus OS reduced motion; off at initial load and selected mid-transition; CSS fades, shimmer, Motion opacity and portal consumers; keyboard focus and validation with completion callbacks suppressed; rapid clicks and repeated Enter; delayed, missing and out-of-order responses; timeout followed by late success; safe retry and conflict handling; editing during a pending save; and close/reopen or unmount during pending work. Verify static status and screen-reader announcements separately from screenshots.

   For the existing settings panel, also verify its real preview/publish lifecycle, refresh/reopen persistence, reversal or rollback, permission boundary and configuration-load fallback. Preserve existing preset names, stored values and history. Record the motion policy, consumer coverage and remaining gaps in the existing design contract, with executable values kept in the current token/configuration source.

This is a proposed design and implementation contract, not a completed fix. The prompt supplies no product repository, installed package version or rendered surface. I used the `generic-product-ui` fallback because “panel” alone does not establish a specific product type; no product-specific pack or local module was loaded. The relevant shared rules were motion, forms, feedback, recovery and accessibility, with design-system token, component-state and governance guidance. Other product packs, visual-style overlays and localization routes were not needed. No new library, framework migration or settings panel is required by this correction. Source inspection, automated tests, rendered interaction checks and accessibility verification remain unperformed; the next implementation step is to inspect the existing adapters, callbacks and save API against this contract.

Use restrained layout motion to explain where tasks went, backed by text and accessible controls. This is a targeted React web-application interaction; mobile browser widths do not activate a native-mobile product route.

For insertion, reveal the task in its actual position with a brief entrance and static “Added” indicator. For reordering, let neighboring cards shift coherently while preserving identity, selection and focus. Use stable task IDs as React keys; final DOM order must match real data order. For offscreen or filtered destinations, explain the location and offer “Show task” instead of unexpectedly scrolling or changing filters. Keep frequent commands immediately usable.

Reuse the existing animation engine first. If coordinated layout and enter/exit behavior needs a provider, Motion for React is a reasonable candidate for this concrete need; CSS suffices for simple highlights and fades. Before adoption, inspect components, package manifest and lockfile, then verify current official APIs, compatibility, license, maintenance and dependencies. Avoid overlapping engines and reuse established motion values.

Provide visible, keyboard-operable “Move up,” “Move down” and “Move to column” actions with equivalent permissions and outcomes to dragging. Preserve focus on the moved task or its action, announce the destination/position politely, and support cancellation. Touch dragging must coexist with scrolling. Mutations, validation and focus restoration must not depend on animation completion.

For remote updates, preserve reading position, active drafts and focus. Consolidate background changes into restrained indicators and useful announcements; do not animate every update. Resolve concurrent moves through the application's actual version/conflict contract, preserving meaningful local work. Distinguish pending optimistic movement from server confirmation; explain rejection or rollback persistently when action is needed. Do not invent locking, merging or Undo support.

Respect reduced-motion preferences from first render and when they change mid-transition. Replace large movement with immediate placement and static destination information. If an existing product policy supports off, remove fades too. Apply the resolved policy to CSS and independent consumers as well as the provider; reduced mode alone is not necessarily fully off. Owner preferences cannot override a request for less motion.

Proposed mobile verification:

- Exercise insertion, same-column and cross-column moves, rapid repeats, cancellation, interruptions and remote changes during a drag or edit. Confirm final order, focus, preserved drafts and no duplicate mutations.
- Test narrow/intermediate widths, rotation, long labels, large text/zoom and supported themes/directions. Check clipping, sticky-header focus obstruction, reachable controls and practical touch targets.
- Test touch scrolling, visible non-drag actions, keyboard-only operation and screen-reader announcements. Compare normal, reduced and off behavior, including preference changes during motion.
- On representative mobile hardware and realistic long lists, compare route payload, interaction responsiveness, rendering work and memory against the baseline. Avoid per-frame full-app state updates; measure before claiming performance gains.

# Proposed settings-page redesign

Keep the existing plugin settings destination inside `wp-admin`. Use a restrained WordPress-native page with a compact operational summary above the configuration form. This is a plan only: no product code, settings, dependencies, or environment changes are proposed for execution now.

The primary route is `wordpress-plugin`. The affected local surfaces are settings/configuration and a limited diagnostics/status summary. A status summary does not by itself activate a dashboard route or justify a separate application shell.

## Establish the page contract

Before implementation, inventory the actual fields and status sources. For each setting, record its user-facing purpose, frequency and consequence, dependencies, default and effective value, capability, existing option key and save scope. Identify the current menu entry, page hook, submission path, validation rules and supported WordPress versions. Reuse the existing design handbook or observed page baseline for typography, spacing and colors.

The plugin's fields, source code, supported versions and current screen were not supplied. Group names, dimensions and compatibility therefore remain provisional; do not invent configuration categories or operational capabilities to fill a layout.

## Page composition

1. **Page identity:** preserve the current WordPress entry point and page title. Add one concise sentence explaining the settings' scope. Keep the admin menu, toolbar and unrelated notices intact.
2. **Operational summary:** a compact, read-only section showing the real subsystems that matter to this plugin. Each item identifies the subsystem, textual state, consequence, last checked time and a contextual link to an existing diagnostic or relevant setting. Prioritize actionable problems while retaining useful healthy context.
3. **Settings form:** group actual fields by administrator intent and dependency. Start with ordinary headings and sections; a short form needs neither tabs nor search. Use one local navigation system only if independent topics justify it. Keep prerequisites, consequential explanations and errors visible.
4. **Save area:** retain the existing save model and make its scope explicit. For an existing whole-page submission, use one “Save Changes” action after the form. Show unsaved and durable save/error feedback near that scope. Status links or refresh controls must not submit the settings form or discard edits.

Use a readable content width, restrained section boundaries and existing host-compatible spacing. At narrow widths, stack fields and summary items in the same semantic order. Labels, help, errors and actions should wrap without clipping. Do not add a plugin appearance panel, dark mode or new global navigation for this page.

## Component selection

For this explicitly redesigned, plugin-owned settings surface, use stable public `@wordpress/components` controls. This is the supplied Skill's settings convention, not a universal requirement for every WordPress screen. It applies even if the form is small.

| Need | Planned choice and reason |
| --- | --- |
| Short text or technical value | `TextControl`, with a persistent label, associated help/error and appropriate input type and direction. |
| Boolean setting | `CheckboxControl` or `ToggleControl`, chosen for the field's meaning. In an explicitly saved form, changing the control remains a draft; explain that save is required. Preserve disabled dependent values. |
| Small fixed choice set | `RadioControl` when comparing visible alternatives helps; otherwise `SelectControl`. Keep the existing stored values and defaults. |
| Save action | `Button`, with the correct submit behavior, explicit scope, busy state and duplicate-request protection. |
| Save result or validation summary | Persistent local `Notice` plus field-level errors. A transient toast cannot be the only recovery information. |
| Secondary settings | Plain sections first. If disclosure is justified, verify a stable, compatible disclosure component such as `CollapsibleCard`; otherwise record the genuine compatibility gap and a bounded semantic HTML composition. Do not default to inspector-oriented `Panel`/`PanelBody`. |
| Operational summary | Semantic headings and a small list or description list for subsystem, state and freshness. Use text and optional icons as well as color. A local `Notice` suits an actionable warning; `Spinner` plus status text suits a real pending check. The settings-only library mandate does not automatically govern operational presentation. |

`SearchControl` is conditional on demonstrated settings volume/findability. If needed, search only authorized names, help and intent aliases; selection must reveal and focus the actual field while preserving drafts and hidden validation errors. Do not index secrets or field values.

`DataViews` and `DataForm` are not defaults for this settings form or small summary. Consider them only if an actual operational collection requires list/filter/edit interactions, after compatibility review. Do not introduce experimental/private controls, a new component library, or a build pipeline solely for presentation.

## Truthful operational state

Distinguish ready, degraded, blocked, checking, stale/unknown and disabled/not configured. Use only states supported by the actual source. Show the timestamp of the underlying check, rather than the page render time; never infer health from a stored credential or represent missing information as healthy.

Keep configuration presence, authorization, health and background-work state distinct where those concepts exist. Accepted or scheduled work is not completed work. Preserve useful stale information with a clear warning if refresh fails. An optional refresh must be a supported read operation with its own capability and loading/error state; it must not silently start processing. Recovery commands belong at their existing operational destination and require their existing authorization. No new retry, maintenance or destructive action is assumed.

## Preserve implementation contracts

- Retain option names, storage shape, defaults, sanitization/validation and the existing Settings API or other submission contract. Component rendering does not require a new REST route. Preserve field names and submitted value semantics, including booleans and omitted fields.
- Retain server-side capability checks and nonce generation/verification for the actual action. Distinguish page access, status visibility and configuration editing; do not substitute role names or UI hiding for authorization. Keep existing permitted read-only behavior.
- Model loading, edited, saving, confirmed saved, rejected and unknown save outcomes separately. A load failure must not expose default-looking values as stored configuration or allow an unsafe save. Retain valid edits after validation errors; reveal hidden invalid fields. Do not clear newer edits when an older submission is acknowledged. Reconcile an uncertain write before retrying. Inspect the existing concurrent-edit contract rather than promising unsupported conflict prevention.
- Reuse the existing asset strategy. Load required WordPress dependencies and component styles only on the owned settings hook. Preserve script translations; avoid duplicate React or Gutenberg activation. Keep layout styles scoped to the plugin with logical properties and existing semantic tokens.
- Verify selected controls and important props against both the minimum supported and current supported host. Inspect any actual dialogs/popovers outside the root for styles, direction and focus. The candidate's specimen evidence is not this plugin's runtime evidence.

## Planned acceptance checks and current limits

After implementation is separately requested, compare the same real page before and after inside `wp-admin`, including expanded/collapsed navigation, toolbar and notices. Exercise initial load and load failure, unsaved edits, successful and rejected saves, duplicate submission, edits during saving, uncertain responses and applicable concurrent editing. Check retained stored values and drafts, not only visible messages. Test full, limited and denied capabilities plus invalid/expired nonce handling using the existing security model.

Inspect normal and narrow widths, keyboard flow, visible focus, zoom/reflow, labels/error associations and meaningful status announcements. Exercise healthy, warning, failed, checking and stale status without losing form input. Test actual supported language/direction and appearance contexts; conversation language does not establish the product locale. Persian-facing UI would require the Persian-writing specialist before linguistic acceptance.

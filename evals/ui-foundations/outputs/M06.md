### Supported settings

| Setting or behavior | Supported contract |
| --- | --- |
| Motion level | An owner-configurable enum: **Off**, **Subtle**, **Standard**, or existing accepted equivalents. It is the ceiling for motion within the appearance system's existing authorized scope. Do not add a new global/tenant/admin scope selector by implication. |
| Off | Immediate state changes with no animated transitions, including fades. Preserve static progress, status, focus, content, and all actions. Off must not leave an invisible overlay or unfinished cleanup. |
| Subtle | A prepared low-motion treatment for useful state changes and continuity. Its exact duration, easing, displacement, and affected interactions come from reviewed product tokens. No decorative looping or motion that delays work. |
| Standard | The existing approved normal treatment, still bounded by product constraints and reduced-motion policy. It is not permission for arbitrary animation. |
| Default | The existing approved default, linked to its actual source. That value is unknown here. If none exists, propose Subtle for a task-heavy product; do not silently activate it as an owner-approved default. |
| Personal motion preference | Reuse an existing permitted preference, if present, to inherit or reduce the owner's ceiling. Do not introduce another settings page or grant new preference permissions merely for this addition. OS accessibility protection works even without a personal settings page. |
| Effective motion status | Read-only explanation of the resolved behavior and its source, for example, “Reduced motion is active because of your device setting.” Distinguish the published selection, private draft selection, and actual effective policy. |
| Preview, publish, history, restore defaults, rollback | Reuse the existing lifecycle and permissions. Restore motion defaults affects this section through a draft; it does not reset unrelated appearance choices or immediately publish. |

Duration/easing bounds belong to the design system, and need verified source links before implementation acceptance. No numeric range or library is selected by this document.

### Protected precedence

Apply locked product and accessibility constraints throughout resolution. Start from valid design-system defaults, apply the validated published owner's ceiling, reconcile permitted personal preferences, and apply the current OS accessibility preference. A private preview substitutes its draft only within the authorized preview context.

| Inputs | Required outcome |
| --- | --- |
| Owner Standard; OS reduced | Reduced-motion treatment, regardless of the owner preference. |
| Owner Off; personal Standard or stale stronger preference | Off. A preference cannot raise the owner ceiling. |
| Owner Standard; personal Off | Off. |
| Owner Subtle; personal Standard | At most Subtle, further reduced by OS constraints. |
| Policy or client preference not yet resolved | Static, usable initial content; no initial burst of animation. |

For reduced motion, replace large movement, parallax, and looping effects with immediate changes or a useful brief non-spatial alternative. This is distinct from Off, which also removes fades. On the web, observe `prefers-reduced-motion` initially and when it changes. A provider's reduced-motion option alone does not prove Off works: CSS, imperative animations, copied components, icons, and independent consumers must follow the same resolved policy.

### Draft, publication, and recovery

1. **Edit privately.** Bind each draft to its owner, authorized scope, draft revision, and base published revision. Enforce read/write/preview permissions at the trusted boundary. Another administrator's ordinary session, public configuration endpoint, and shared cache must not receive the draft. Saving or previewing must not change anyone else's active appearance. Show “Draft saved” separately from “Published.”
2. **Preview and validate.** Show current versus draft level and the effective accessibility-adjusted result on representative real interactions. Preserve valid input on errors. Validate types, supported presets, schema compatibility, permissions, and protected constraints before publish. Preview cannot bypass the owner's own reduced-motion preference. Cancel/discard leaves the published version unchanged.
3. **Publish atomically.** Reuse the existing concurrency mechanism to compare the base published revision at the trusted write boundary. Publish one complete validated snapshot, preserving unrelated settings. Only after authoritative confirmation show the active version and success. Refresh/invalidate scoped caches so users receive a consistent version.
4. **Handle two administrators explicitly.** If both start from revision A and administrator one publishes B, administrator two's draft based on A must receive a conflict. Preserve that draft, show the changed fields and current revision, and allow reconciliation and revalidation against B. Do not silently overwrite, merge incompatible snapshots, or use last-write-wins for shared appearance governance.
5. **Handle uncertain publication.** A lost response does not establish failure. Keep the draft and mark the outcome unknown; reconcile the operation/active revision through the existing system before retrying. Prevent duplicate publication and history entries using its supported retry/concurrency contract.
6. **Preserve history.** Each publication records actor, time, scope, schema version, prior/base revision, changed fields, and validation result in immutable or reconstructable history. Log relevant validation failures, publications, resets, and rollbacks without exposing private draft content through public logs.
7. **Restore and roll back safely.** Restoring motion defaults creates a reviewable draft from known defaults. Rollback requires existing permission, compatibility validation, and the same concurrency protection; it creates a new active version derived from the chosen historical configuration. Preserve the old versions. An old history entry cannot restore executable content or defeat current motion constraints.

For older persisted presets, distinguish owner configuration from personal preferences. Preserve still-valid choices; use explicit, versioned mappings only where old and new semantics are equivalent. Do not rename or reset accepted choices silently. If no safe mapping exists, exclude the invalid value from active resolution and use the current safe permitted default, retaining the prior raw configuration only where needed for migration/audit. Reconcile stored preferences after migration, owner changes, permission changes, and rollback. Notify users when the resulting change is material.

A missing, partial, invalid, unsupported-version, or failed configuration load must never resolve a private draft or assemble incompatible fragments. Use a validated complete last-known-good published snapshot where compatible; otherwise use a complete safe default policy. Retain the last valid configuration and history without treating fallback as a new publication. Apply current OS/personal reductions to the fallback as well. Show an actionable load/retry message and identify fallback or stale state in the owner panel. Keep publication unavailable when its current base cannot be established. Initial render and failed-load behavior must remain usable and cannot enable stronger motion than the effective constraints allow.

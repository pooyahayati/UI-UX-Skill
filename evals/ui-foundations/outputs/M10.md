Render a usable static interface on the server and on the first client render. Enable optional motion only after the client has resolved the effective policy. Treat animation as a presentation effect of application state; it must never determine whether navigation, validation, saving, focus restoration, or cleanup completes.

I would use the following contract for this React web application. These are proposed implementation requirements; no product source or running application was supplied.

| Stage | Required behavior |
| --- | --- |
| Server render | Render the correct visible content and semantic open/closed, selected, pending, or error state. Use a static motion policy while the OS preference is unknown. Include this policy and its CSS in the initial response, so an entrance animation cannot run before JavaScript starts. |
| First client render | Use the same initial policy, markup, and attributes as the server. Do not branch the initial component tree on `window`, `matchMedia`, or client storage. Do not hide essential content behind initial opacity, an offscreen transform, or a hydration-only reveal. |
| After hydration | Read the OS preference, load and validate relevant configuration/preferences, then resolve one effective policy. Updating the policy should enable eligible future interactions without replaying an entrance animation or remounting controls. |
| Configuration unavailable | Continue rendering with a safe, validated fallback. Preserve any known request for less motion. A failed fetch must not implicitly turn motion on or reset saved preferences. |
| Preference change or interruption | Immediately apply the stricter policy, stop incompatible running effects, and settle the presentation to the current semantic state. Preserve focus, drafts, and interaction availability. |
| Route change or unmount | Dispose of effects owned by the leaving surface. Remove obsolete overlays and release their interaction locks through the component's supported lifecycle, regardless of whether an exit animation finishes. |

Resolve motion once and feed every consumer from it. Keep the readiness of inputs separate from their values: an unknown OS preference is not equivalent to “no preference.” A conceptual resolver is:

```text
unknown required input, without a trustworthy fallback -> static/off
owner off or personal off                          -> off
otherwise                                         -> permitted owner/user level
OS requests reduced motion                        -> further restrict that level
```

An owner setting is a ceiling. A personal preference can lower it, and the OS accessibility preference remains effective even if there is no personal settings page. For example, owner standard plus OS reduced uses the reduced treatment; owner off plus user standard remains off. Keep accepted existing presets and defaults rather than silently renaming or resetting them.

Reduced and off need different behavior. Reduced motion removes large movement, parallax, and loops; a brief non-spatial alternative may remain when it helps communicate a state change. Off removes all animated transitions, including fades. Both preserve immediate state changes, visible focus, static loading/status feedback, accessible names, and usable actions.

The initial CSS must enforce the static policy before hydration. Scope transitions and keyframes to an explicitly resolved motion state, and retain a `prefers-reduced-motion` rule as a browser-level safeguard. Cover pseudo-elements, smooth scrolling, and portalled controls where applicable. A provider alone cannot protect these consumers. Make the static final styles explicit: suppressing a keyframe is insufficient if the base style still leaves content invisible.

For existing Motion-based controls, `MotionConfig reducedMotion="user"` is useful but does not implement a complete off mode: the documented reduced treatment disables transform/layout animation while other values, such as opacity, may still animate. Copied animated controls need their own source review and an adapter to the same policy. Inspect their CSS, nested providers, local defaults, layout/exit effects, imperative calls, and animated icons. Preserve their accessible primitive behavior and existing customizations. No new animation library is necessary merely to establish this contract; exact package APIs and compatibility would need verification against the actual installed versions before implementation.

For configuration-load failure, retain the last complete, schema-valid configuration for the correct scope and resolve it again against current OS/user restrictions. Do not combine partial responses or reuse a private preview as published configuration. If no trustworthy configuration or preference value exists, use a bundled static/off fallback. During an unresolved failure, do not increase motion above the last effective restriction. Keep the failure distinguishable from a successfully loaded current configuration, offer the existing recovery path where useful, and avoid persisting the fallback over the user's saved choice. A late successful response must be checked for scope/revision freshness before it updates policy; it must not replay past animations.

Keep subscriptions and teardown ownership explicit. An application-level motion service can subscribe to preference changes once and survive ordinary route changes; dispose of that subscription when its owner unmounts. Route-owned effects should cancel animation handles, animation frames, timers, observers, and event subscriptions, and abort or ignore obsolete route-owned configuration requests. Late callbacks must not update a new route or restore focus to a detached trigger. Cleanup should be idempotent so repeated setup/teardown remains safe. Do not cancel a shared service or infer cancellation of a server operation merely because a route unmounted.

Close overlays and remove hidden interactive content using their primitive's supported lifecycle. Release owned scroll locks, inert state, focus traps, and input-blocking backdrops even when motion is disabled, interrupted, or fails to load. Restore focus to a surviving meaningful target, or let the destination route establish its appropriate focus. Keep business actions tied to explicit user/application events and real request outcomes, never solely to `animationend`, `transitionend`, an exit delay, or an animation completion callback. This also prevents rapid interaction or missing callbacks from skipping validation or duplicating mutations.

Before accepting an implementation, I would exercise a CSS transition and a copied animated control through cold server loads with delayed JavaScript/configuration, reduced motion already enabled, off mode, hydration, invalid/missing/failed configuration, preference changes during animation, rapid repeated activation, and navigation during exit. Verify no initial burst, no hydration mismatch, no invisible or input-blocking leftovers, no leaked listeners, no lost drafts or duplicate actions, and correct keyboard/focus/status behavior. Test the actual product's supported contexts; the conversation language does not establish a product locale.

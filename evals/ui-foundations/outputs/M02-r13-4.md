Use **subtle, interruptible layout motion** to show where tasks move, backed by text and accessible status feedback. Treat this as a targeted React web-application interaction; testing it on phones does not require a separate native-mobile design route.

- **New tasks:** insert the task in its actual sorted position, briefly ease nearby cards into their new positions, and mark the new card with a restrained highlight plus a text label. Preserve stable task IDs, selection, focus and scroll context. If the task is offscreen or excluded by a filter, name its destination and offer “Show task”; do not silently change filters or jump the viewport.
- **Reordering:** animate the changed card and nearby layout only enough to explain the new position. Avoid bounce, long travel, celebratory effects, looping pulses or whole-board entrance sequences. Keep the next action immediately available; repeated operations should settle into the latest valid state rather than queue animations. A short duration around 150–200 ms is a starting proposal to test, not an established product requirement.
- **Non-drag access:** provide visible “Move task” controls with destination column and position choices, usable by touch, keyboard and assistive technology. Optional move-up/down actions can accelerate local reordering. Support cancellation; keep focus associated with the task after a successful move and announce its destination and position. Dragging may supplement this path, never replace it. Keep ordinary touch scrolling usable and avoid making the whole card intercept every swipe.
- **Remote updates:** avoid moving items under a user who is editing or dragging. Reconcile through the product’s actual concurrency rules; for unrelated updates, a batched “Board updated” indication and explicit review action can preserve context. A remote change to the active task requires a visible conflict or updated-state explanation before committing against stale data. Never silently overwrite local work. Do not steal focus, force-scroll or announce every incoming event. An unobtrusive summary and destination information should remain available even when movement is suppressed.
- **Truthful feedback:** distinguish a pending local move from a server-confirmed result. On rejection, reconcile to authoritative state, explain what happened and preserve task input. Offer retry, reapply or undo only where the backend supports those semantics. Task mutation, cleanup, cancellation and focus restoration must work without waiting for animation completion.

For implementation, first inspect the existing animation engine, components and package setup. Reuse compatible behavior. If the board needs coordinated insertion and layout continuity beyond simple CSS transitions, **Motion for React** is a justified candidate. Keep one engine responsible for each animated element/property. AutoAnimate is a narrower alternative for simple list changes; it is not an extra engine to add alongside Motion by default. A task board does not by itself justify a timeline engine or a new component foundation. Verify current official APIs, compatibility, maintenance, license and dependency impact before adoption; no dependency has been inspected or installed here.

Resolve motion preferences consistently across the provider, CSS and independent effects. Respect the system’s reduced-motion preference on first render and when it changes. Reduced mode should use immediate placement or a brief non-spatial cue; full Off must also eliminate fades while retaining labels, status, focus and every action. A provider’s reduced-motion option alone is not a complete Off implementation. Existing owner settings may cap motion, while accessibility and personal preferences can reduce it further. This recommendation does not require a new settings panel. Keep the initial interface static and usable until preferences resolve.

On mobile, verify the following with rendered interactions on representative supported browsers and real devices where available:

| Scenario | Acceptance evidence to collect |
| --- | --- |
| Add and reorder | Users can identify the new column and position, including offscreen or filtered destinations. DOM reading order matches real data order; focus, selection and scroll position remain meaningful. |
| Touch and non-drag use | The full move flow works by tapping controls, with reliable target spacing and visible labels. Scrolling, cancellation, edge scrolling during drag, and switching columns do not cause accidental moves. Also test a narrow window with keyboard input. |
| Assistive technology | Test a supported mobile screen reader through creation, move, cancel and failure. Check names, focus return, destination announcements and batched remote notices; no live-region flood. |
| Normal, reduced and Off | Change the system preference during movement. Check CSS and other consumers as well as provider components. Off has no residual fades; each mode preserves equivalent information and actions. |
| Interruption and remote changes | Exercise rapid repeated commands, remote edits during drag/edit, reconnect, failed saves, uncertain responses and navigation away mid-transition. No duplicate mutations, stale overwrite, stranded overlays or lost drafts. |
| Narrow layout and text | Test portrait/landscape, large text, zoom, long task names and the product’s supported directions/themes. Keep destination controls, focus indicators and actions visible; do not mirror task order merely because layout direction changes. |
| Performance | Compare before/after on a representative slower phone with a realistic long board and bursts of remote updates. Record interaction delay, dropped frames/long tasks, render work and added route payload. Avoid per-frame whole-app state updates and animating every offscreen card; evaluate virtualization only when board size warrants it. |

The meaningful success check is whether people can locate a changed task and continue working, with and without motion or dragging. Observe representative users performing those tasks rather than treating a smooth screenshot as proof.

Plan the page as a WordPress-native settings extension with a compact operational summary. Keep its existing place in `wp-admin`, the host navigation and toolbar, and the plugin's established save contract. This is a design proposal only: no product repository, running page, or screenshots were provided, so the current layout, options, compatibility, and behavior have not been inspected or verified.

The primary route is `wordpress-plugin`, using its settings and diagnostics/operations modules. A summary on a settings page does not by itself justify a separate dashboard route or application shell.

1. Establish the bounded baseline before implementation.

   Inventory the actual settings, dependencies, default/effective values, field names and option keys, storage shape, validation/sanitization, submission handler, page/action capabilities, nonce handling, and available status sources. Inspect the supported WordPress versions, existing asset pipeline, product languages, and approved design baseline. These are planned checks, not findings. Retain existing typography, palette, navigation, and supported appearance behavior; this task does not call for a new appearance panel or plugin dark mode.

2. Organize the page around configuration and operational readiness.

   Start with the page title and a short purpose statement, followed by a compact “Operational status” region. Show blockers prominently with a useful next step; keep healthy status concise so routine configuration remains the main task. A status item should identify the subsystem, its state, consequence, and freshness when that information exists. Link to existing diagnostics or Site Health when relevant, rather than embedding logs or creating a duplicate health screen.

   Follow with settings grouped by actual user intent and dependency. Use headings and sections for a short form. Add tabs only if the inventory reveals substantial independent topics; add collapsible advanced settings only for genuinely secondary options. Do not hide prerequisites or validation errors inside a closed group. Keep one explicit “Save Changes” action with clear scope if that matches the existing save model. Do not introduce immediate saving or per-section submission merely for the redesign.

   Record page/field widths, heading levels, spacing, label/help/error placement, and the save-action position against the real baseline before rendering. Prefer labels above controls and a single-column flow at narrow widths; allow the summary and action groups to wrap without changing reading order. Keep the save action discoverable without introducing a sticky bar unless the page length warrants it and it can be verified inside the host.

3. Select components by the actual data and task.

   The candidate's convention requires stable public `@wordpress/components` for standard controls on this authorized redesigned, plugin-owned settings surface—even if the form is small. This is a settings-specific convention, not a claim that WordPress requires the library for every admin screen. Importing one library button while hand-building all standard inputs would not meet it.

   | Surface or need | Proposed choice | Reason and boundary |
   | --- | --- | --- |
   | Short text or technical value | `TextControl` | Persistent label, appropriate input type, help, controlled value, and associated validation. Use only for fields actually present. |
   | Boolean setting | `ToggleControl` or `CheckboxControl` | Choose according to meaning; clearly state that changes await saving when applicable. Preserve disabled dependent values. |
   | Small known choice set | `SelectControl` or `RadioControl` | Preserve existing stored values and understandable labels; avoid a custom dropdown. |
   | Save or supported local action | `Button` | Explicit action/scope, supported busy and disabled behavior, and duplicate-submit protection. |
   | Save result, error summary, or page-local blocker | `Notice` | Durable, appropriately severe feedback. Field errors remain associated with their controls; a toast is insufficient for failure or uncertain outcomes. |
   | Genuinely secondary settings | `PanelBody`, only if needed | Accessible disclosure with errors discoverable; ordinary primary settings remain visible. |
   | Read-only operational summary | Semantic heading plus list, description list, or a small table when comparison warrants it | Status is information, not an editable setting. Text labels carry meaning; color or icons only reinforce it. A simple summary does not need a new component library. |
   | Active status check, if already supported | Existing suitable button and `Spinner` with status text | Reuse WordPress components where useful, without extending the settings mandate to diagnostics. A spinner means checking, not successful completion. |

   Use semantic HTML for structural headings and layout. Define each selected control's relevant focus-visible, disabled/read-only, checked/selected, busy, invalid, and expanded states through its supported semantics; focus must remain distinct from selection, and read-only values must not become unexplained disabled controls. Reuse the existing component styling and approved tokens rather than creating a new design system. Record a genuine stable-component gap and a bounded compatible composition if one appears. Do not silently replace the required settings controls with another library, experimental/private exports, or unverified opt-in flags. A confirmation `Modal` is appropriate only if an existing consequential action requires it; the redesign does not introduce reset or maintenance actions by default.

4. Preserve data, security, and truthful state.

   Keep existing option keys, value encodings, storage, Settings API or existing endpoint contracts, and server validation/sanitization. If the plugin already submits a Settings API form, preserve that path and its nonce fields; ensure component values serialize to the existing field names, including unchecked booleans. React-rendered controls do not require a new REST endpoint or storage migration.

   Preserve the exact existing capability checks for page access, configuration changes, status visibility, and operational actions. Do not replace them with role-name assumptions. Server authorization and nonce verification remain authoritative; hiding or disabling controls is only presentation. Expose useful read-only settings/status only where the current permissions allow it, with a clear explanation of why editing is unavailable.

   Distinguish initial loading, load failure, edited, saving, confirmed saved, rejected, and unknown outcomes. A failed initial load must not present defaults as stored values or permit an overwrite. Preserve valid edits on rejection and only report success after authoritative confirmation. For an existing asynchronous save, retain edits made after the submitted snapshot; if a response is lost after a possible commit, reconcile stored state before retrying. Preserve unrelated option sections. Inspect the existing concurrent-edit contract and report any limitation rather than promising protection that the backend lacks.

   In the status summary, distinguish ready, degraded, blocked, checking, stale/unknown, and disabled/not configured as supported by actual evidence. Show the last checked time only when available; otherwise make freshness unknown. A saved credential is not proof of a healthy connection, and a scheduled or accepted job is not completed work. Expose retry/cancel/repair controls only where an existing authorized backend action supports them. Keep ordinary feedback local; use a global WordPress notice only for a condition that matters beyond this page.

5. Integrate and validate later within the existing stack.

   Reuse the current build approach. Enqueue assets only on the owned settings-page hook, declare WordPress shared dependencies and `wp-components` styles, and use matching generated asset metadata for a bundled build. A small existing no-build approach can use the public WordPress globals with explicitly maintained dependency handles. Do not bundle a second React runtime or enable Gutenberg just to render settings. Load translations for the actual script handle/domain and scope layout styles to the plugin surface with logical properties. Inspect any portal-rendered overlay outside the root as well.

   Before implementing, verify each selected control and important prop against the plugin's actual minimum and current supported WordPress hosts. Record the source verification date and runtime outcome. The candidate guide's historical specimen evidence is not product compatibility evidence.

   Proposed acceptance checks are: before/after rendering inside real `wp-admin` at normal, intermediate, and narrow widths with expanded/collapsed menus and notices; keyboard flow and visible focus; associated labels/help/errors; text zoom, reflow, contrast, non-color status, and useful screen-reader announcements; supported languages/directions and host appearance modes only. Exercise valid/invalid saves, preserved values, denied capability and invalid nonce with no data change, initial-load failure, duplicate submission, applicable edits-during-save and uncertain-response recovery, hidden-group errors, and supported status states. Inspect overlays if used, and run the product's available build, lint, integration, and accessibility checks. Verify retained stored values as well as visible feedback.

Keep the existing native, server-paginated list and compose a matching report-detail page inside the current WordPress admin shell. Thousands of records make bounded server queries important; they do not, by themselves, justify replacing the interface. Reuse the current no-build script and core shared dependencies for small enhancements where needed.

This is an **operational report workspace**, with English, left-to-right content. The administrator’s task is to find a report, inspect it, and use an available row action. Keep the existing plugin entry point and report URLs; introduce no settings or appearance panel.

| Surface | Recommended composition and behavior |
| --- | --- |
| Report list | “Reports” heading, labeled search and existing filters, an explicit “Apply filters” action, visible active-filter scope and “Clear filters,” then the native table. Preserve the existing query contract. |
| Table | Make the report name or identifier a real detail link. Prioritize the existing fields needed to distinguish reports; for example, status and date only where those fields exist. Use text for status meaning. Keep row actions attached to the correct report and reachable by keyboard and touch. Do not make the entire row the only navigation target. |
| Pagination and sorting | Retain the existing server pagination, page size and supported sorts. Show the result range and total only when supplied by the server. Sorting and filtering must describe the complete matching collection, rather than silently processing only the current page in the browser. |
| Report detail | Use a dedicated page with “Back to reports,” the report identity, relevant existing metadata, supported actions and clearly headed report content. Preserve the list’s filters, search, sort and page on return through the existing navigation mechanism. A long report should not be squeezed into a modal. |
| Narrow admin width | Wrap or stack filter controls; keep labels visible. Prioritize report identity and useful summary fields. Allow contained horizontal scrolling when column comparison requires it, and retain access to details and actions. Account for the WordPress toolbar, notices and collapsed navigation. |

Reuse WordPress typography, spacing, native table conventions, buttons and notices. Native HTML controls are a practical default for this surface. Existing stable public `@wordpress/components` controls can be reused when they improve a specific interaction and are available in the supported host; an operational list does not inherit a settings-only component mandate. Do not duplicate shared React dependencies or introduce a second component framework.

Keep selection behavior explicit if the current list supports it: preserve its existing semantics, distinguish selected rows from all matching reports, and never silently extend an action across unseen pages. Expose only existing, capability-authorized actions; retain their current authorization and confirmation behavior. Distinguish “No reports yet” from “No reports match these filters,” preserving the filter input in the latter. A request failure must not appear as an empty result. Show action success only after confirmation from the existing handler, and keep actionable failure messages visible.

**The conditional alternative is public `DataViews` from `@wordpress/dataviews`.** Its dataset layouts, search, filters and sorting are relevant when users demonstrably need richer collection interactions that the native list cannot reasonably supply. `DataForm` targets record editing; it is not needed merely to display report details, and this request does not establish an editing requirement. These distinctions follow the [official package documentation](https://developer.wordpress.org/block-editor/reference-guides/packages/packages-dataviews/).

Before adopting that alternative, establish all of the following:

- A concrete workflow benefit, such as necessary alternate collection layouts or substantially richer supported filtering, outweighs migration and maintenance cost.
- A compatible package version, public API, WordPress entrypoint, shared dependencies and required styles are established for WordPress 6.8 and the actual no-build setup. Current documentation describes `@wordpress/dataviews/wp` for builds using `@wordpress/scripts`; that does not establish a ready-to-use global for this plugin. [Package integration guidance](https://developer.wordpress.org/block-editor/reference-guides/packages/packages-dataviews/)
- View changes can map to the existing server query and pagination contract without a new backend, REST layer or storage migration. Loading every report into the browser would not be an acceptable substitute.
- Any necessary dependency installation, bundling or framework change has separate authorization. Until then, retain the native approach.

This is a design recommendation only. No implementation, installation or runtime verification was performed. WordPress 6.8 package compatibility remains unverified. A later authorized implementation should check list-to-detail return behavior, supported row actions, capability-limited access, empty/error states, keyboard focus, table semantics and narrow-width behavior in the real admin shell.

Routing used: the WordPress plugin Product Pack and its operational-collection guidance, with shared navigation, filter-input, hierarchy, feedback, recovery, responsive and accessibility rules. No secondary product route or WordPress settings module was needed; no new design-system foundation, language variant or motion treatment is proposed.

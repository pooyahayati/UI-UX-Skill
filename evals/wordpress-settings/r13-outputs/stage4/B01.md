# Implementation handoff: report settings

Redesign the existing settings page as a single-column form with two controls and one explicit save action. Retain its current menu entry, page slug, Settings API submission path, option keys, defaults, permissions, and validation rules. The product remains English and left-to-right.

This is an implementation proposal based on the supplied request. No plugin source, running site, or screenshots were supplied or inspected. Nothing was installed and no site testing was performed.

Use semantic HTML for the page heading, form, and layout. No tabs, search, collapsible sections, cards, sidebar, modal, or new appearance settings are needed for two fields.

Proposed layout values, to be checked against the existing page baseline:

- Keep the normal `.wrap` admin container; constrain the form content to about `40rem`.
- Stack labels, controls, help, and errors. Make the report-name input `width: 100%` up to about `28rem`.
- Use approximately `24px` between field groups and before the action row. Preserve host typography, focus treatment, and component styling.
- Keep the save action in normal document flow below both settings. Let its adjacent unsaved-status text wrap on narrow screens.
- Scope any layout CSS to the plugin’s settings root and use logical properties such as `max-inline-size` and `margin-block`. Do not override global WordPress styles or component internals to create a new theme.

Copy about what email actually sends, recipients, scheduling, and prerequisites must come from the current plugin behavior. Do not add a “Send test email” action or claim that saving demonstrates delivery.

## Integration without a build pipeline

1. **Keep PHP and the existing Settings API form as the submission owner.** Preserve the current POST destination, `settings_fields()` group and hidden fields. Replace only the two field presentations, the action presentation, and relevant plugin-owned feedback. Keep registration and sanitization callbacks intact.

2. **Use a small maintained JavaScript file with public globals.** Use `wp.element` and `wp.components`; use `wp.i18n` for translatable interface strings. Avoid JSX/transpilation, package installation, bundled React, new REST endpoints, or Gutenberg activation.

3. **Declare actual dependencies explicitly.** Enqueue the script only when `admin_enqueue_scripts` receives the existing settings-page hook suffix. The maintained dependency metadata should include `wp-element`, `wp-components`, and `wp-i18n` if used. Enqueue `wp-components` styles and make the plugin’s scoped stylesheet depend on them. Load translations for the actual script handle and the existing text domain. Version assets using the plugin’s existing strategy.

4. **Bridge component drafts into the existing form names.** Initialize state from safely encoded server values. Map the email value using the plugin’s explicit boolean encoding; do not use generic truthiness on strings such as `"0"`. Keep exactly one canonical submitted value for each field. A robust option is components for editing plus hidden inputs carrying the exact existing names and serialized values. Components in that arrangement must not also submit duplicate names. Synchronize the canonical inputs on every change and ensure the submit handler captures the latest draft, including an immediate Enter submission after typing.

5. **Preserve the original unchecked behavior.** If false is represented by an omitted field, a hidden zero, or a particular string today, preserve that contract. Never let the toggle’s unchecked state inadvertently drop or erase another setting. If settings share an array option, preserve every unrelated member using the existing merge/submission behavior.

6. **Keep a usable failure path.** Preserve the original PHP-rendered form as a progressive fallback until the component interface is initialized successfully. Replace its editable inputs only after successful mounting, so fallback inputs and hidden bridge values cannot submit duplicate names. If trusted initial values cannot be obtained, show a durable failure message and prevent saving default-looking replacements. A valid “option absent, use registered default” state is different from a load failure.

7. **Retain server authority.** JavaScript validation may assist the user but cannot replace existing validation, sanitization, nonce, or capability checks. Escape server-provided content appropriately and pass initial values as safely encoded data, not interpolated executable strings.

8. **Keep save feedback truthful.** Editing either field shows a local unsaved indicator. The first valid submit captures the draft and prevents duplicate submits; disable repeat actions without disabling the canonical named payload fields before serialization. Clear the dirty state only after an authoritative successful response. A redirect alone, toggle change, or click is not proof of success.

For rejected submissions, show the real error next to the relevant field and preserve safe edits through the existing recovery mechanism. If the existing Settings API flow cannot return drafts after validation, record that gap and propose a bounded recovery addition separately; do not claim that a component migration fixes it. Likewise, ordinary full-page POST navigation cannot guarantee recovery from a lost response: check authoritative saved values before repeating an uncertain save, and do not introduce background writes or browser draft storage silently. Preserve the existing concurrent-edit contract; do not promise conflict detection if the backend lacks it.

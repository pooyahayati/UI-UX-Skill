Do not adopt the proposal across every settings screen. Keep the existing no-build integration and make separate decisions for the short settings form and the report collection.

| Surface or package | Practical decision |
| --- | --- |
| Short settings form | Use version-verified, stable public `@wordpress/components` controls through `wp.components` for any subsequently authorized redesign. Keep ordinary headings, related fields, help, and an explicit save action. |
| Thousands of report records | Evaluate `DataViews` specifically for this collection’s search, filters, sorting, pagination and row actions. Preserve an adequate existing native list while compatibility and integration remain unverified. |
| Current `@wordpress/ui` | Do not adopt it for this release. Its current documentation labels it experimental and explicitly says it is not supplied as a `window.wp` script. |

The important distinction is between current package documentation and the runtime your supported WordPress version actually provides. The current `@wordpress/ui` package can change incompatibly and does not fit a direct replacement of your existing globals-based script.

[Official UI package documentation](https://developer.wordpress.org/block-editor/reference-guides/packages/packages-ui/)

For the short form, the candidate skill’s settings convention requires stable public `@wordpress/components` when a redesign is authorized—even for a small form. That is this project convention, not a universal WordPress requirement. Audit authorization alone does not authorize replacing existing controls. Suitable candidates are `TextControl`, `ToggleControl` or `CheckboxControl`, `SelectControl`, `Button`, and `Notice`, according to the actual fields. Use persistent labels, associated help/errors, and truthful saving/saved/failed states. There is no need for DataViews, settings search, tabs, decorative cards, or a theme provider merely to modernize a short form.

Keep the no-build delivery model:

- Use public `wp.components` and `wp.element` APIs; do not paste bare npm imports or JSX into the shipped browser script.
- Maintain explicit script dependencies for the globals actually used, such as `wp-components`, `wp-element`, and `wp-i18n` when applicable. Do not depend on the editor having loaded them.
- Enqueue assets only on the owned plugin screen. Make `wp-components` a stylesheet dependency, load translations for the actual script handle, and scope layout styles to the plugin surface.
- Preserve existing option names, submission/storage contracts, server-side capabilities, nonces and sanitization. React controls do not require a new REST endpoint or a different save model.

The official components documentation confirms the stylesheet dependency and warns indirectly against root-only styling assumptions: popovers normally render under the document body. Any future overlay work must check its focus, direction, inherited styles and stacking there too.

[Official components integration guidance](https://developer.wordpress.org/block-editor/reference-guides/packages/packages-components/)

For the report screen, `DataViews` is a plausible task fit, not an automatic performance upgrade. `DataForm` belongs only if users actually edit report records; it is not the default renderer for plugin configuration. The current documentation specifies `@wordpress/dataviews/wp` for WordPress integrations built with `@wordpress/scripts`, plus required styles. That guidance does not establish a supported no-build entrypoint on WordPress 6.8. Verify the exact host’s public exports, registered handles, transitive dependencies and styles before selecting it; do not unlock private APIs or add a build pipeline to make it fit.

[Official DataViews and DataForm documentation](https://developer.wordpress.org/block-editor/reference-guides/packages/packages-dataviews/)

Keep data access bounded: use the existing server pagination/filtering contract, show accurate totals and active filters, distinguish no records from no matches, and preserve navigation and selection semantics across pages. Do not fetch and render thousands of records simply because the component accepts an array. If the existing backend cannot support the proposed interaction, record that limitation separately rather than silently redesigning storage or APIs.

`ThemeProvider` and the public semantic tokens from `@wordpress/theme` are distinct from a site theme or `theme.json`. The official package documentation explicitly states that installing a newer package does not upgrade WordPress’s supplied runtime. For this task, reuse existing scoped styles and approved values. A later theming proposal would need a verified public provider/export on every supported host, appropriate token CSS, and a concrete need; private compatibility exports are not a solution.

[Official theme package and runtime compatibility guidance](https://developer.wordpress.org/block-editor/reference-guides/packages/packages-theme/)

Before implementation, make a small compatibility record for each selected control and important prop: minimum supported host, current supported host, source/package revision, stylesheet requirements, and observed runtime result. The official 6.8 maintenance branch currently lists `@wordpress/components` at `29.5.4` and `@wordpress/dataviews` at `4.15.4`; that is version context, not proof that today’s examples or exports work on the original 6.8 release. Retrieval of the exact original-release sources was unsuccessful, so I am not certifying those APIs here. Avoid experimental/private exports and unverified `__next*` flags; any documented styling-transition exception needs testing on both hosts.

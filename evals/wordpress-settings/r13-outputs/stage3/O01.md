Keep the existing native, server-paginated list and compose a focused report-detail page around it. This is an operational WordPress plugin workspace. Its record volume and filters do not, by themselves, justify replacing the current list or adding a component framework.

Use native semantic markup and the plugin’s existing WordPress styling first. Where the current script already uses core-shared components, reuse stable public controls available in WordPress 6.8 for small interactions. `@wordpress/components` is an option here, not a mandatory replacement for the native table, filters, or detail layout. This task has no settings surface.

| Area | Recommended composition and behavior |
| --- | --- |
| Entry and heading | Keep the existing plugin menu destination and WordPress admin shell. Use “Reports” as the page heading, with any existing result count scoped to the active query. |
| Search and filters | Keep the existing supported filters. Give each a visible label; place frequent filters beside search and let less frequent filters expand below. Use “Apply filters” for the existing server request and “Clear filters” for recovery. Show active constraints even when the extra filter area is collapsed. |
| Report list | Retain the native semantic table. Make report identity a detail link; show available status/date fields and the few columns needed to compare records. Use text for status, with color only as reinforcement. Enable sorting only where the existing server supports it. |
| Row actions | Retain existing action names, permission checks, confirmation behavior, and server handlers. Use links for navigation and buttons for operations. Make actions reachable by keyboard and touch, with names that identify the report; avoid hover-only access. |
| Pagination | Preserve server pagination and the current page size. Display the current result range and total when supplied by the server. Filters and sorting operate on the full matching dataset, not merely the loaded page. Applying a changed filter starts at the first page. |
| Detail | Use a dedicated, addressable detail page: “Back to reports,” report identity/status, a concise metadata summary, report content, and existing actions. Use headings, definition lists, and tables according to the content. Preserve filter, sort, and page context on return. A read-only detail view needs no editing form. |

If selection already exists, retain its documented scope across pagination and return navigation. Make “selected on this page” versus “selected across results” explicit; do not silently expand an action to unseen records. Row actions alone do not require adding bulk selection.

Keep the no-build script and existing shared runtime. Do not ship another React copy. Any reused core component must have its registered script dependency and required stylesheet loaded on the plugin page, rather than assuming the editor has loaded it elsewhere. WordPress documents the registered-dependency/global pattern for shared packages. [WordPress package reference](https://developer.wordpress.org/block-editor/reference-guides/packages/)

Thousands of stored records remain manageable when the browser receives one bounded page. Retain that boundary; do not fetch everything for client-side filtering or introduce virtualization without evidence that the displayed page is a bottleneck. On narrow admin widths, wrap the filter toolbar, preserve report identity and actions, and keep a scrollable table where comparison requires columns. Detail content can stack naturally.

Specify distinct states for “No reports yet,” “No reports match these filters,” and a failed request. Preserve filter input on failure. Show action success only after server confirmation, and keep failure feedback beside the affected row or detail action. Native table headers, visible focus, properly labeled controls, and predictable return navigation form the accessibility baseline.

The alternative worth evaluating is public `DataViews` from `@wordpress/dataviews`, when actual requirements demand several layouts, richer field-driven filtering, configurable columns, or repeated collection screens whose custom behavior is becoming expensive to maintain. `DataForm` belongs in that evaluation only if report editing is required; it is not necessary merely to display report details. The package documents those separate purposes. [DataViews package documentation](https://developer.wordpress.org/block-editor/reference-guides/packages/packages-dataviews/)

That alternative is not a drop-in choice for this no-build scope. Do not assume a public `wp.dataviews` global or `wp-dataviews` core handle: WordPress’s stated distribution approach is for plugins to bundle the package. [WordPress maintainers’ distribution guidance](https://make.wordpress.org/core/2026/09/18/roadmap-to-7-2/#comments)

A future, separately authorized evaluation would need a version compatible with WordPress 6.8, its documented WordPress entrypoint, required styles, and its dependency relationship with the core-shared runtime. Current documentation describes `@wordpress/dataviews/wp` for WordPress builds using `@wordpress/scripts`; that does not establish availability in the current no-build script or compatibility of the newest package with 6.8. WordPress explicitly documents the risks of mixing bundled packages with host-supplied dependency versions. [Runtime compatibility guidance](https://developer.wordpress.org/block-editor/contributors/code/package-runtime-compatibility/)

Even then, preserve server pagination and existing data/action contracts. A component choice would not justify introducing REST endpoints, storage changes, or a framework migration.

Settings-specific component guidance, other Product Packs, appearance configuration, and a new design system were outside scope.

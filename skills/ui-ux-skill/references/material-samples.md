# Selected Material samples and handbook integration

Load only for selected Material and authorized new/broad sample work. A narrow
repair or read-only audit does not start phases or create a handbook. Reuse
[the sequential workflow](design-foundation-workflow.md) as the single phase
authority; this overlay adds Material-specific traceability, not another gate
system. Keep [handbook authority](design-handbook.md) and one canonical DESIGN.md.

## First inspectable slice

Choose screens from the actual job and scope, not a generic dashboard/gallery.
Explain one professional treatment, its audience/task rationale and tradeoff.
Map only the relevant [component families](material-components.md) to settled
[foundation sources](material-foundations.md). A filled action, outlined field
or grouped card must consume the existing palette/font/spacing/state roles;
do not replace them with a provider's default theme or native-platform pixels.
Use actual approved fonts/weights and product language/direction, independent of
chat language. Record real compact/intermediate/wide targets justified by content.

Use the existing stack or a bounded code-native specimen when no product runtime
exists. Label synthetic content/actions and unsupported/custom composition.
Do not call a native HTML approximation a tested provider API or complete M3
Expressive implementation. Significant component/provider adoption still uses
[stack fit](material-stack-fit.md). No sample generation implies library install,
new features, rollout, admin controls or customer approval.

## Trace the same design, not parallel proposals

In existing sample and decision rows retain:

- selected mode evidence and scope, professional personalization rationale;
- relevant local guides and official sources/review dates, distinguishing source
  observations from the agent's product inference and implementation exceptions;
- actual executable value sources and consumers, font assets and weights;
- sample/handbook revisions, phase, parent approved primary/dark identity;
- focused feedback, correction delta, accepted versus pending decisions,
  actual actor/source/date or explicit unknown, exclusions and next action;
- observed viewport/theme/locale/states, capture/font limits and untested behavior.

Present only the primary proposal initially. Record dark needs as planned, not
an upfront theme switch or hidden prebuilt variant. After actual scoped primary
approval, derive dark semantic treatment without changing accepted typography,
spacing, structure or behavior. After dark approval, confirm secondary need and
named owner authority, or record monolingual N/A with its source. Existing valid
production themes/locales are preserved; this governs new proposal sequencing.

A correction reuses the same proposal; preserve the last approved baseline and
invalidate only actually dependent approvals. Approval evidence must bind the
viewed sample and matching handbook, not just the style name or latest filename.
An uploaded image or maintainer instruction acceptance is not a fictional
customer's consent. Tests may exercise synthetic approval records but must label
them as tests, never populate the actual specimen with invented owner events.

## Handoff

Return one usable viewing location, current revisions/phase, applied source links,
specific feedback request, observed task/recovery results and honest limits.
Use the existing authorized same-Skill delegation contract only when useful and
permitted; keep one handbook writer. No agent available/authorized: proceed with
one writer and disclose that no independent model evaluation ran. Do not require
the maintainer to approve an unrelated specimen's taste to accept Skill source.
Runtime appearance remains a separate boundary; full mode evaluation is R9.6.

# Incremental Design Decisions and Bounded Handoffs

Use before a meaningful later UI slice, new design need or material feedback against an existing foundation. A small copy correction needs only the affected baseline/check, not full discovery. This reference owns incremental impact and handoff decisions; [design-handbook.md](design-handbook.md) owns document authority, [design-foundation-workflow.md](design-foundation-workflow.md) owns staged visual approval, and [specialist-routing.md](specialist-routing.md) owns delegation permission.

## Inspect once, continue from the baseline

Read the canonical product `DESIGN.md`, last approved decisions and pending changes, authoritative requirements, affected implementation/token/configuration sources and actual handoff. Identify the baseline revision and which approvals cover this slice. Preserve known palette, typography, spacing/density, semantic icons, primary language/direction, responsive priority, features and permissions; do not ask the owner to choose them again without new material evidence.

An observed interface without a handbook can support a narrow correction, but is not invented owner approval. Audit-only work returns findings without file changes. Do not force document migration, a runtime panel or a full interview merely to continue development.

## Classify the change before asking

| Change | Smallest appropriate response |
| --- | --- |
| Compatible local detail within approved/delegated scope | Resolve with a product-fit rationale; reuse foundation and existing authority. Record a meaningful contract change, not every incidental edit. |
| Newly necessary design treatment for an already approved job | Identify the missing interaction/state and affected surfaces; recommend one foundation-aligned treatment. Ask only if a material owner choice remains. A design treatment does not approve new features. |
| Appearance preference | Distinguish it from changed user needs. An agent/reference preference does not replace accepted values; a material owner-requested change is a pending proposal until scoped authority exists. |
| Strategic change to foundation, navigation, workflow or runtime contract | Explain affected components, states, themes/locales, settings/consumers and dependent approvals. Obtain owning scope/approval before broad application; use partial rediscovery only for affected choices. |
| Conflict, stale handoff or unclear approval | Keep the last demonstrably approved baseline. Name contradictory sources and the one owning decision; clarify or return the affected proposal rather than publishing parallel values. |

Resolve implementation mechanics from the current stack. A novel screen must not import another product's conventions. Do not treat a new audience, role, data field, permission or integration as a harmless style choice. Route that feature/security/data decision to the engineering/product owner.

## Recommend, record and verify only the delta

Explain the new need, one professional recommendation, its reason/tradeoff and the precise unanswered question if any. Allow correction or explicit scoped delegation; silence or an unsubmitted default is not authority. An already sufficient approval should not trigger another interview. Keep the main coding conversation concise, but expose required owner decisions rather than hiding them in a handoff.

Update only affected handbook decisions, workflow/requirement coverage, sample/evidence links and material open questions. Retain the previous accepted baseline/provenance; record the proposed revision, source, rationale, affected scope and status. Do not recopy live token/config values into an independently editable handbook authority. Routine bounded admin value changes use product configuration/history, not manual handbook edits. A changed configurability contract or icon meaning/family boundary needs impact assessment; no nonexistent admin control/storage is claimed implemented.

Assess dependent samples and approvals explicitly. An isolated label/state can reuse unaffected foundations; a global palette/font/spacing change may require primary re-review and then affected dark/localized re-review under the existing sequential workflow. Do not restart all phases for unchanged decisions or silently carry approvals to changed ones. Language two remains conditional, not an automatic response to new feedback.

Choose the cheapest relevant verification for the delta: actual responsive/state/action evidence when UI changes, consumer/config checks when applicable, or source review for a documentation-only proposal. Record actual performed checks separately from planned/unavailable ones. A passing build or returned agent summary never substitutes for the affected rendered/functional evidence. Missing evidence leaves the affected acceptance pending, not every unrelated task blocked.

## Bounded assignment and return

For substantial design work, recommend a same-Skill assignment only when authorized and available. Otherwise the lead performs the bounded work directly; do not spawn an agent, create another chat or add a specialist registry entry by implication. Assign one handbook writer for a revision; parallel contributors return proposals, not competing canonical edits.

Pass only the necessary context:

- current objective, approved product/job/feature scope, affected surfaces and exact writable paths;
- canonical handbook path, baseline revision, scoped approval sources and relevant pending decisions;
- settled foundation/source links, stack, actual language/direction, current review phase and protected invariants;
- genuinely new need, authorized actions, acceptance criteria and required evidence/known tooling limits.

The return identifies baseline and proposed revision, recommendation/decisions with rationale, accepted versus proposed changes and authority, actual changed paths, affected components/settings/approvals, sample/evidence locations, performed and unperformed checks, conflicts and remaining owner/engineering decisions. State explicitly when no code, sample, runtime setting or agent was produced.

The lead rereads the current baseline before integrating the return. If it moved, compare relevant decisions and reconcile stale changes; never overwrite concurrent user edits or silently apply an older proposal. Review scope, foundation consistency, authority and evidence, then record acceptance, requested changes or the unresolved blocker. Lead acceptance of a scoped contribution is not customer visual approval, whole-product completion, merge, release or deployment authority.
